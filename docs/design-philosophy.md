# Agent Harness 设计哲学

> 基于系统论、控制论、信息论（SCI 论）的设计原则

## 概述

Agent Harness 项目的设计深受"老三论"（系统论、控制论、信息论）的启发。这三门二十世纪四十年代创立的系统理论，为我们构建复杂 AI Agent 协作系统提供了坚实的理论基础。

```
系统论 → 信息论 → 控制论
  ↓        ↓        ↓
看见整体 → 理解沟通 → 实现目的
```

---

## 一、系统论（Systems Theory）— 看见整体

### 1.1 核心思想

系统论由美籍奥地利生物学家贝塔朗菲（L. von Bertalanffy）创立，核心观点包括：

- **整体性**：系统功能大于各部分之和（涌现性）
- **关联性**：要素之间相互依存、相互影响
- **层级性**：系统具有层次结构，可分解为子系统
- **目的性**：系统趋向特定目标运动
- **动态性**：系统处于积极的运动状态

### 1.2 在 Agent Harness 中的体现

#### 整体性：四角色分离架构

```
┌─────────────────────────────────────────────────────────────┐
│                      Agent Harness 系统                      │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐  │
│  │ Planner │───→│ Reviewer│───→│ Executor│───→│Evaluator│  │
│  │  规划   │    │  审查   │    │  执行   │    │  评估   │  │
│  └─────────┘    └─────────┘    └─────────┘    └─────────┘  │
│       ↑                                            │        │
│       └────────────── 反馈回路 ────────────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

四个 Agent 单独存在时功能有限，但组合成一个系统后，能够实现复杂的软件开发任务自动化。

#### 关联性：清晰的输入输出依赖

| Agent | 输入来源 | 输出去向 | 关联关系 |
|-------|---------|---------|---------|
| Planner | 用户需求 | Reviewer | 计划 → 审查 |
| Reviewer | Planner | Executor/Planner | 审查通过 → 执行/重规划 |
| Executor | Reviewer | Evaluator | 执行结果 → 评估 |
| Evaluator | Executor | End/Executor/Planner | 评估结论 → 完成/修复/重规划 |

#### 层级性：Orchestrator 作为协调层

```
┌─────────────────────────────────────┐
│         Orchestrator 层              │
│    （全局协调、路由决策、状态管理）     │
├─────────────────────────────────────┤
│          Agent 执行层                │
│  Planner │ Reviewer │ Executor │ Evaluator │
├─────────────────────────────────────┤
│          工具能力层                  │
│  filesystem │ code │ execution │ network │
└─────────────────────────────────────┘
```

#### 目的性：原子能力定义

每个 Agent 都有明确的目的和边界：

```yaml
# Planner 的目的性示例
atomic_capabilities:
  execution:
    task_types:
      - requirement_analysis      # 目的：理解需求
      - task_decomposition        # 目的：拆解任务
      - architecture_design       # 目的：设计方案
```

#### 动态性：自适应工作流

系统不是静态的，而是根据执行状态动态调整：

```
正常流程：Planner → Reviewer → Executor → Evaluator → End
异常流程：Planner ← Reviewer (NEEDS_REVISION)
         Executor ← Evaluator (NEEDS_IMPROVEMENT)
         Planner ← Executor (plan_defect_detected)
```

### 1.3 设计原则

**原则 1.1：整体性优先**
- 设计时先考虑系统整体目标，再分解到各 Agent
- 确保单个 Agent 的优化不会损害整体性能
- 定期评估系统涌现性（是否产生 1+1>2 的效果）

**原则 1.2：明确边界**
- 每个 Agent 必须有清晰的输入边界和输出边界
- 避免 Agent 职责重叠或真空地带
- 通过原子能力声明明确能力边界

**原则 1.3：层级清晰**
- 上层（Orchestrator）负责协调，下层负责执行
- 同层 Agent 通过标准接口通信
- 避免跨层级直接调用

## 二、信息论（Information Theory）— 理解沟通

### 2.1 核心思想

信息论由美国数学家香农（C. Shannon）创立，核心观点包括：

- **信息是消除不确定性的度量**
- **信道容量**决定信息传输效率
- **编码/解码**确保信息准确传递
- **噪声**影响信息质量
- **冗余**提高信息可靠性

### 2.2 在 Agent Harness 中的体现

#### 信息度量：置信度评分

```yaml
# 信息质量的量化
atomic_capabilities:
  introspection:
    confidence_scoring:
      enabled: true
      factors:
        - requirement_clarity     # 需求清晰度
        - domain_familiarity      # 领域熟悉度
        - technical_feasibility   # 技术可行性
```

#### 信道：协作接口

```yaml
# 标准化的信息传输通道
collaboration_interfaces:
  - name: plan_delivery
    format: structured_yaml     # 编码格式
    content: execution_plan      # 信息内容
  
  - name: feedback_reception
    format: structured_yaml
    content: review_feedback
```

#### 噪声处理：问题上报机制

```yaml
# 识别并处理信息噪声
feedback:
  issue_escalation:
    - type: requirement_ambiguous
      description: 需求不明确（噪声源）
      action: request_clarification  # 降噪处理
    
    - type: technical_constraint
      description: 技术约束无法满足
      action: escalate_to_user
```

#### 信道容量：上下文限制

```yaml
# 防止信息过载
context:
  max_tokens: 8000              # 信道容量上限
  priority:                     # 信息优先级
    - TASK.md
    - CLAUDE.md
    - DECISIONS.md
```

### 2.3 设计原则

**原则 2.1：信息结构化**
- 所有 Agent 间通信必须使用结构化格式（YAML/JSON）
- 明确信息的 Schema，便于解析和验证
- 避免非结构化文本导致的信息失真

**原则 2.2：置信度量化**
- 每个 Agent 输出必须包含置信度评分
- 低置信度信息需要额外验证或人工确认
- 建立置信度阈值机制

**原则 2.3：噪声控制**
- 识别信息传递中的噪声源（需求模糊、上下文缺失等）
- 建立噪声检测和处理机制
- 关键信息采用冗余设计（多路径确认）

**原则 2.4：信道优化**
- 根据信息重要性分配信道资源
- 高优先级信息优先传输
- 定期评估信道容量是否满足需求

## 三、控制论（Cybernetics）— 实现目的

### 3.1 核心思想

控制论由美国数学家维纳（N. Wiener）创立，核心观点包括：

- **反馈是控制的基础**：系统通过反馈调节行为
- **负反馈维持稳定**：纠正偏差，保持稳态
- **正反馈促进变化**：放大信号，推动转变
- **黑箱方法**：通过输入输出研究系统
- **自组织**：系统自发形成有序结构

### 3.2 在 Agent Harness 中的体现

#### 反馈回路：Agent Loop

```
         ┌─────────────────────────────────────────┐
         │                                         │
         ▼                                         │
┌─────────────────┐    ┌─────────────────┐        │
│   Planner       │───→│   Reviewer      │        │
│  (制定计划)      │    │  (负反馈：审查)  │        │
└─────────────────┘    └────────┬────────┘        │
                                │                 │
                                ▼                 │
┌─────────────────┐    ┌─────────────────┐        │
│   Evaluator     │←───│   Executor      │        │
│  (负反馈：评估)  │    │  (执行计划)      │        │
└────────┬────────┘    └─────────────────┘        │
         │                                        │
         │ 正反馈：PASS → 任务完成                  │
         │ 负反馈：NEEDS_IMPROVEMENT → 返回修复     │
         └─────────────────────────────────────────┘
```

#### 负反馈：质量控制

```yaml
# 负反馈维持系统稳定
reviewer:
  decision:
    output_signals:
      - name: needs_revision
        description: 需要修改（负反馈）
        trigger: 存在必须修改的问题
        action: 返回 Planner 重规划

evaluator:
  decision:
    output_signals:
      - name: needs_improvement
        description: 需要改进（负反馈）
        trigger: 存在必须修复的问题
        action: 返回 Executor 修复
```

#### 正反馈：进度推进

```yaml
# 正反馈推动系统向目标前进
- name: execution_complete
  description: 执行完成（正反馈）
  trigger: 代码实现并通过测试
  action: 进入 Evaluator 评估

- name: pass
  description: 评估通过（正反馈）
  trigger: 需求实现且测试通过
  action: 任务完成
```

#### 控制机制：动态路由

```yaml
# Orchestrator 的控制逻辑
routing_logic:
  - from: reviewer
    signal: approved
    to: executor              # 正反馈：推进到下一阶段
  
  - from: reviewer
    signal: needs_revision
    to: planner               # 负反馈：返回修正
  
  - from: evaluator
    signal: needs_improvement
    to: classify_and_route    # 智能路由：根据问题类型决定
```

#### 稳态：终止条件

```yaml
# 系统达到稳态的条件
termination_conditions:
  success:
    - verdict: PASS           # 评估通过
    - verdict: EXCELLENT      # 优秀完成
  
  failure:
    - max_iterations_exceeded  # 超过最大迭代次数
    - cycle_detected           # 检测到循环
    - user_abort               # 用户终止
```

### 3.3 设计原则

**原则 3.1：反馈驱动**
- 每个阶段必须有明确的反馈机制
- 反馈必须及时（避免过长延迟导致失控）
- 区分正反馈（推进）和负反馈（修正）

**原则 3.2：闭环控制**
- 建立完整的反馈回路，避免开环执行
- 每个输出都应有相应的反馈验证
- 通过闭环实现自适应调节

**原则 3.3：分层控制**
- 局部控制：Agent 自控制（如 Executor 的自测）
- 全局控制：Orchestrator 的路由决策
- 避免控制冲突，明确控制优先级

**原则 3.4：预防性控制**
- 不仅依赖反馈（事后），增加前馈（事前预测）
- 预测可能的问题并提前干预
- 建立预警机制

## 四、三论融合的设计框架

### 4.1 设计检查清单

在设计和评审 Agent Harness 的架构时，使用以下检查清单：

#### 系统论检查清单

- [ ] 该设计是否考虑了整体目标？
- [ ] 各组件的边界是否清晰？
- [ ] 组件之间是否存在不必要的耦合？
- [ ] 是否存在单点故障风险？
- [ ] 系统是否具有涌现性（1+1>2）？
- [ ] 是否考虑了系统的动态演化？

#### 信息论检查清单

- [ ] 信息传递是否有明确的格式和协议？
- [ ] 是否考虑了信息丢失/噪声的处理？
- [ ] 关键信息是否有冗余或确认机制？
- [ ] 信道容量是否匹配信息量？
- [ ] 是否对信息质量进行了量化？
- [ ] 低置信度信息是否有处理机制？

#### 控制论检查清单

- [ ] 每个阶段是否有明确的反馈机制？
- [ ] 反馈是否及时？
- [ ] 是否存在正反馈导致的失控风险？
- [ ] 系统是否能自适应环境变化？
- [ ] 是否建立了有效的终止条件？
- [ ] 控制层级是否清晰？

### 4.2 反模式警示

以下设计违背三论原则，应避免：

| 反模式 | 违反原则 | 正确做法 |
|--------|---------|---------|
| Agent 职责重叠 | 系统论-边界 | 明确划分职责边界 |
| 非结构化通信 | 信息论-编码 | 使用结构化格式 |
| 无反馈执行 | 控制论-反馈 | 建立反馈回路 |
| 无限循环 | 控制论-稳态 | 设置终止条件 |
| 信息过载 | 信息论-信道 | 限制上下文大小 |
| 单点故障 | 系统论-整体 | 增加冗余设计 |

## 五、演进方向

基于三论的设计哲学，Agent Harness 的演进方向包括：

### 5.1 系统论方向：涌现性增强

- **并行协作模式**：支持多个 Agent 同时处理不同子任务
- **群体智能模式**：多个同类 Agent 投票决策
- **自组织网络**：Agent 自发形成协作关系

### 5.2 信息论方向：信道优化

- **信息质量度量**：建立更完善的信息质量评估体系
- **智能压缩**：自动压缩冗余信息，保留关键内容
- **多模态通信**：支持文本、代码、图表等多种信息形式

### 5.3 控制论方向：自适应控制

- **预测性路由**：基于历史数据预测最优路由
- **动态参数调整**：根据执行情况自动调整参数
- **多级反馈**：建立更细粒度的反馈控制机制

## 六、总结

Agent Harness 项目以"老三论"为设计哲学基础：

```
┌─────────────────────────────────────────────────────────┐
│                      系统论                              │
│  "将 Agent 视为有机整体，关注涌现性和边界"                │
├─────────────────────────────────────────────────────────┤
│                      信息论                              │
│  "确保 Agent 间高效、准确的信息传递"                      │
├─────────────────────────────────────────────────────────┤
│                      控制论                              │
│  "通过反馈机制实现自适应、目标导向的行为"                 │
└─────────────────────────────────────────────────────────┘
```

这三论不是孤立的，而是相互支撑、层层递进：
- **系统论**提供框架：定义了 Agent 是什么
- **信息论**提供连接：定义了 Agent 如何沟通
- **控制论**提供行为：定义了 Agent 如何实现目标

所有后续设计和优化都应遵循这一哲学框架。
