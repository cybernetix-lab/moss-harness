# moss-harness 设计哲学

> `moss-harness` 不是靠功能堆叠取胜，而是靠更强的系统哲学赢得长期上限。

## 为什么需要更深的设计哲学

如果一个 Agent 系统只追求“把任务做完”，那么它很容易演变成以下几种形态之一：

- 功能越来越多，但系统边界越来越模糊
- 自动化越来越强，但反馈与治理越来越弱
- 记忆越来越多，但信息质量越来越差
- UI 越来越复杂，但事实源越来越不清晰

`moss-harness` 的目标不是做一个“更方便的 Agent 工具箱”，而是做一个**可自动进化学习的超级智能体 harness 底座**。这要求项目在一开始就拥有统一的理论骨架。

这个骨架来自 SCI：

- **系统论**：定义整体、边界、层级与涌现
- **信息论**：定义信息质量、噪声、记忆与信号
- **控制论**：定义反馈、稳态、调节与演化

## 一、系统论：边界、层级与涌现

系统论告诉我们，复杂系统不是零件堆积，而是边界清晰、层级明确、彼此约束的有机整体。

在 `moss-harness` 中，这意味着：

- 系统不能退化为一个没有职责边界的 Agent 池
- 每次执行都必须归属明确的 **Role Lane**
- `mosscli` 只是验证应用，而不是整个系统边界
- orchestration、memory、sandbox、telemetry、governance 必须作为整体来设计

系统论带来的核心收益不是“结构好看”，而是让涌现成为可能。只有在边界清晰的前提下，系统级能力才有机会大于组件之和。

## 二、信息论：记忆、噪声与信号质量

一个会学习的系统，首先必须是一个会处理信息质量的系统。

如果没有信息论 discipline，所谓“记忆系统”最终只会变成：

- 噪声堆积
- 低价值上下文污染
- 不可验证的知识幻觉
- 反馈链路上的信号失真

因此 `moss-harness` 把信息论落实为以下要求：

- 事实优先于叙述
- 关键状态必须落盘并可回放
- 记忆必须服务于降低不确定性，而不是机械囤积上下文
- 观测指标必须具备清晰命名与可比性，例如统一使用 `moss_` 前缀
- Replay 与 Report 必须从事实源出发，而不是从 UI 视角反推

换句话说，记忆不是“存下来就算拥有”，而是“让未来决策获得更高信息质量”。

## 三、控制论：反馈、稳态与受控演化

控制论的价值在于，它让系统不仅能行动，而且能**纠偏**。

一个没有反馈的 Agent 系统，本质上仍然是开环自动化。它可能很能跑，但不会稳定变好。

`moss-harness` 把控制论落实为以下原则：

- 所有关键执行都需要反馈位点
- 演化必须发生在治理边界内
- 控制面与观测面必须分离
- `mosscli serve` 暴露的 Web 面板只能是 **read-only**，不能成为第二控制面
- 任务认领必须遵循事务化顺序：`Fact -> Audit -> Broadcast`

这组约束的目标，不是保守，而是为了让系统可以在更高层次上持续进化。

## 四、四层竞争优势叙事

### 1. 哲学层优势

`moss-harness` 的第一优势，是它不是功能先行、理论补票。

它从一开始就以 SCI 理论统一以下问题：

- 系统边界如何定义
- 信息质量如何保证
- 反馈如何驱动行为调整
- 演化如何在治理中发生

这让它相较于许多通用 Agent 框架，拥有更强的一致性与长期演进方向。

### 2. 能力层优势

`moss-harness` 不是把 orchestration、memory、sandbox、telemetry、governance 看成互不相关的 feature。

它的能力优势在于闭环：

- 编排决定谁做事
- workflow orchestrator 决定阶段如何推进、返工如何回送
- 记忆决定系统记住什么
- 沙箱决定系统如何安全执行
- Telemetry 决定系统如何被看见
- Feedback 决定系统如何被修正
- Governance 决定系统如何在边界内演化

因此，它追求的不是“某个单点能力最强”，而是“整个系统越来越强”。这里的 workflow orchestrator 也不是传统意义上的流程引擎，而是系统论中的秩序生成器、控制论中的反馈路由器。

### 3. 系统层优势

`moss-harness` 的系统层优势来自对不变量的坚持。

最关键的不变量包括：

- **Role Lane ownership**
- **Transactional claiming: `Fact -> Audit -> Broadcast`**
- **Read-only Web observability**
- **`.runtime/moss-harness/` runtime namespace**
- **`moss_` observability contract**

这些不变量使系统在持续增强时仍然可以被解释、被回放、被审计。

### 4. 产品层优势

从产品层看，`moss-harness` 采用的是一种更克制但更有战略价值的路径。

它没有一开始就试图把一切包装成“超级应用”，而是通过 `mosscli` 这个 CLI-first 验证应用来证明底座成立：

- 控制面保持显式、可审计
- Web 面板保持只读、可观测
- 反馈与返工路径可以被真实验证
- 指标、时间线、报告可以形成完整证据链

这种路径让项目在还未全面产品化之前，就先建立了“底座是真的能跑、能看、能纠偏”的可信度。

## 五、设计检查与反模式

### 设计检查清单

在评审任何新能力时，至少检查以下问题：

- 它是否强化了 Role Lane，而不是削弱边界？
- 它是否保留了 `Fact -> Audit -> Broadcast` 的事务顺序？
- 它是否让 Web 观测面保持只读？
- 它是否把信息质量提升为第一等问题？
- 它是否让系统更容易 replay、report、audit？
- 它是否帮助系统更安全地演化，而不是制造新的黑箱？

### 反模式

以下模式违背 `moss-harness` 的哲学方向，应当避免：

- 把 `mosscli` 当成整个项目本体
- 为了交互方便，把 Web 面板演化成写操作入口
- 跳过事实落盘，直接广播状态变化
- 没有指标命名纪律，导致可观测信号不可比较
- 把“更多记忆”误当成“更好记忆”
- 把自动化速度误当成系统进化能力

## 六、演进方向

未来的 `moss-harness` 应该继续沿着以下方向演进：

- 更强的 Orchestration：从固定路径到更高质量的动态编排
- 更强的 Memory：从持久化事实到高信号密度的长期知识体系
- 更强的 Sandbox：从可执行到可控、可复现、可治理
- 更强的 Feedback：从规则纠偏到受控学习与自适应调节
- 更强的 Governance：让系统越强越可控，而不是越强越失真

## 结语

`moss-harness` 的真正竞争优势不在“功能比别人多”，而在：

它试图把超级智能体系统从“会做事的工具”推进为“会学习、会演化、会被治理的底座”。

这就是它优于一般 Agent 框架、个人代理或本地自动化平台的根本原因。
